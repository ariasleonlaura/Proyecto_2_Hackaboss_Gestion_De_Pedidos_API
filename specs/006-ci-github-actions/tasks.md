# Tareas 006 — CI con GitHub Actions: verificar cada cambio y publicar imágenes

Parte de la spec aprobada `specs/006-ci-github-actions/spec.md` y del plan `specs/006-ci-github-actions/plan.md`. Todas las tareas son de **CI/infra** (no hay cambios en el código de `Backend/` ni de `Frontend/`); varias verifican con comandos de backend o frontend, pero los ficheros que se tocan son solo los indicados. Las ejecuciones reales de GitHub Actions solo se pueden comprobar empujando: al final de cada tarea se distingue qué es verificable en local y qué queda para la primera ejecución real (T7, con el usuario).

- [x] **T1. [CI/infra] Esqueleto del workflow: disparadores, permisos, concurrencia y dependencias.**
  Objetivo: dejar el andamiaje del flujo correcto antes de rellenar los jobs.
  Alcance: crear `.github/workflows/ci.yml` (solo la estructura: `name`, `on`, `permissions`, `concurrency` con `cancel-in-progress` condicionado a pull requests y los cuatro `jobs` con sus `runs-on` y `timeout-minutes: 20`; un job de GitHub Actions no puede quedarse sin pasos, así que cada uno lleva un paso provisional `run: echo "pendiente"` que T2-T5 sustituyen por sus pasos reales).
  RF: RF-1, RF-2, RF-3, RF-4, RF-23 (permisos globales `contents: read`), RF-25.
  Hecho cuando (local): el YAML es válido (validador YAML o `docker run --rm -v "$PWD":/repo --workdir /repo rhysd/actionlint:latest -color`); `on` tiene `pull_request.branches: [main]` sin filtro de `types` (drafts incluidos), `push.branches: [main]` (sin otras ramas) y `workflow_dispatch`; `permissions` globales solo `contents: read`; `concurrency` agrupado por workflow + ref con `cancel-in-progress: ${{ github.event_name == 'pull_request' }}` (la comprobación es que el valor sea exactamente esa expresión: solo se cancelan ejecuciones de pull request y las de main no se cancelan, RF-25); los cuatro jobs declaran `timeout-minutes: 20` y un paso provisional (`run: echo "pendiente"`); `publish` declara `needs: [backend, frontend, docker]` e `if: github.event_name == 'push' && github.ref == 'refs/heads/main'` sin `always()`; los otros tres jobs no tienen `if`. (La ejecución de los triggers reales se comprueba en T7 con un PR/push del usuario.)

- [x] **T2. [CI/infra] Job `backend`: compilar y pasar todas las pruebas con Java 17.**
  Objetivo: ejecutar la suite completa del backend en cada comprobación.
  Alcance: `.github/workflows/ci.yml` → job `backend` (checkout, `actions/setup-java` Temurin 17 con `cache: maven`, `mvn -B -f Backend/pom.xml test`).
  RF: RF-5, RF-6, RF-7, RF-24.
  Hecho cuando: en el fichero no aparece ninguna variable `DB_*` en el job; en local, `mvn -B -f Backend/pom.xml test` con Docker en marcha termina en verde (mismo comando que en CI) — verificable en local; que la caché funcione en Actions se comprueba en T7 (segunda ejecución sin descargas desde cero).

- [x] **T3. [CI/infra] Job `frontend`: instalación reproducible, lint y build con Node 22.**
  Objetivo: verificar el frontend con pasos claros y ampliables.
  Alcance: `.github/workflows/ci.yml` → job `frontend` (checkout, `actions/setup-node` Node 22 con `cache: npm` y `cache-dependency-path: Frontend/package-lock.json`, `defaults.run.working-directory: Frontend`, y tres pasos separados: `npm ci`, `npm run lint`, `npm run build`).
  RF: RF-8, RF-9, RF-10, RF-11, RF-24.
  Hecho cuando: en el fichero el lint **no** lleva `--max-warnings` (los avisos no bloquean, RF-9) y los tres comandos son pasos independientes (hueco para un futuro `npm run test`, RF-11); en local pasan `npm --prefix Frontend ci`, `npm --prefix Frontend run lint` y `npm --prefix Frontend run build` — verificable en local; el uso de la caché npm en Actions se comprueba en T7.

- [x] **T4. [CI/infra] Job `docker`: validar el Compose, comprobar la contraseña vacía y construir las dos imágenes.**
  Objetivo: dejar construidas (sin publicar) las imágenes que luego subirá `publish`.
  Alcance: `.github/workflows/ci.yml` → job `docker` (checkout; `DB_PASSWORD=ci-dummy docker compose config --quiet`; paso que exige que `DB_PASSWORD="" docker compose config` termine con código distinto de cero; `docker/setup-buildx-action`; dos `docker/build-push-action` con `push: false`, `load: true`, caché GHA de **ámbito propio** (`cache-from: type=gha,scope=backend` / `scope=frontend` y `cache-to: type=gha,mode=max,ignore-error=true,scope=backend` / `scope=frontend`, para que las dos imágenes no compartan caché; el `cache-to` del backend lleva el comentario `# mode=max: necesario para que la capa de dependencias del backend (spec 005, go-offline) llegue a la caché`), `labels: org.opencontainers.image.source=${{ github.server_url }}/${{ github.repository }}` en ambos, la de frontend con `build-args: VITE_API_URL=http://localhost:8080/api`; `docker save` + `actions/upload-artifact` con `overwrite: true` e `if: github.event_name == 'push' && github.ref == 'refs/heads/main'`).
  RF: RF-12, RF-13, RF-14, RF-19 (la construcción que luego se publica), RF-24, RF-25 (implícito en el flujo).
  Hecho cuando (local): `DB_PASSWORD=ci-dummy docker compose config --quiet` sale 0; `DB_PASSWORD="" docker compose config` sale distinto de 0; `docker build -t img/backend:ci Backend` y `docker build --build-arg VITE_API_URL=http://localhost:8080/api -t img/frontend:ci Frontend` terminan sin errores; `git status` no muestra cambios en `docker-compose.yml` ni en `Backend/`/`Frontend/`. Por lectura del fichero: cada build declara su `scope=` propio (backend/frontend) en `cache-from` y `cache-to`, la línea `cache-to` del backend lleva el comentario literal `# mode=max: necesario para que la capa de dependencias del backend (spec 005, go-offline) llegue a la caché` (motivación del usuario: sin ese comentario, alguien puede "simplificar" bajándolo a `mode=min` y la caché Maven dejaría de funcionar en el CI sin aviso), ambos pasos llevan `labels: org.opencontainers.image.source=...` y `actions/upload-artifact` tiene `overwrite: true`. Que el artefacto solo se suba en main se revisa por lectura del `if` y se confirma en T7.

- [x] **T5. [CI/infra] Job `publish`: login en GHCR, etiqueta del commit y `latest` condicional.**
  Objetivo: publicar solo en push a main verde, con las reglas de re-ejecución.
  Alcance: `.github/workflows/ci.yml` → job `publish` (permisos del job `contents: read` + `packages: write`; `download-artifact` + `docker load`; cálculo de `IMAGE_PREFIX` en minúsculas con `tr`; `docker/login-action` a `ghcr.io` con `GITHUB_TOKEN`; etiquetado y push de la etiqueta del commit en las dos imágenes; comparación `git ls-remote` de la punta de `main` con `github.sha` y push de `latest` solo si coinciden, con el token pasado al paso como `env: GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}` y usando `"$GITHUB_TOKEN"` en el script, sin interpolar `${{ secrets.GITHUB_TOKEN }}` dentro de él).
  RF: RF-16, RF-17, RF-18, RF-19, RF-20, RF-21, RF-22, RF-23.
  Hecho cuando: solo `publish` tiene `packages: write` (búsqueda en el fichero: una única aparición); no hay ningún `secret` configurado más allá de `secrets.GITHUB_TOKEN`; el paso de `latest` declara `env: GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}` y el script lo usa como `"$GITHUB_TOKEN"` (nada de `${{ secrets.GITHUB_TOKEN }}` dentro del `run`); en local, un script de prueba **temporal y fuera del repositorio** (no debe aparecer en `git status`) con SHAs ficticios cubre los tres casos — (a) punta == sha → subiría `latest`, (b) punta != sha → no lo subiría, (c) re-ejecución de commit antiguo → nunca `latest` — y el nombre calculado para `APIGestionDePedidosProyecto2HackABossMejorado` es `ghcr.io/<dueño>/<repo>` en minúsculas. (El push real a GHCR solo puede comprobarse en T7.)

- [x] **T6. [CI/infra] README: insignia y documentación de la CI (y anotación en MEMORY).**
  Objetivo: que el estado se vea de un vistazo y que queden documentados los pasos manuales y la advertencia de la imagen.
  Alcance: `README.md` (badge arriba + sección "Integración continua") y `MEMORY.md` (decisión CI + aprendizajes, manteniendo ≤ ~50 líneas).
  RF: RF-14 (parte documental), RF-27, RF-28.
  Hecho cuando: la insignia apunta a `https://github.com/<dueño>/<repo>/actions/workflows/ci.yml/badge.svg` con el slug real de `git remote get-url origin` y enlaza al workflow; la sección explica las tres comprobaciones, que la publicación ocurre solo en push verde a main, los pasos manuales (activar Actions en el fork; hacer públicos a mano los DOS paquetes — backend y frontend — tras la primera publicación) y el aviso de **no hacer `docker push` manual a ghcr.io antes de la primera publicación del CI** (una publicación manual crearía los paquetes fuera del flujo, sin pasar las comprobaciones, y condiciona la primera ejecución), y la advertencia de que la imagen del frontend lleva incrustada `http://localhost:8080/api`, solo es válida en local con Docker Compose y la demo futura se construirá aparte con su dirección pública; MEMORY.md refleja la decisión. (La insignia en verde real solo se ve tras la primera ejecución, T7.)

- [ ] **T7. [CI/infra] Verificación global local + primera ejecución real (la ejecuta el usuario).**
  Objetivo: confirmar que todo el conjunto está en verde antes de considerar terminada la spec.
  Alcance: comprobaciones locales sobre los ficheros de T1-T6 + la primera ejecución real en GitHub (paso del usuario: activar Actions en el fork y empujar).
  RF: todos (RF-1 a RF-28).
  Hecho cuando:
  - **Local**: `mvn -B -f Backend/pom.xml test` en verde (compilación y pruebas del backend); `npm --prefix Frontend ci`, `npm --prefix Frontend run lint` y `npm --prefix Frontend run build` en verde; `DB_PASSWORD=ci-dummy docker compose config --quiet` OK y `DB_PASSWORD="" docker compose config` falla; sintaxis del workflow válida (validador YAML o `docker run --rm -v "$PWD":/repo --workdir /repo rhysd/actionlint:latest -color`); `git status` solo muestra `.github/workflows/ci.yml`, `README.md`, `MEMORY.md` y `specs/006-ci-github-actions/` (el script de simulación de `latest` de T5 es temporal y vive fuera del repo, así que no aparece).
  - **Primera ejecución real (usuario)**: un PR hacia main (incl. draft) muestra los tres checks en verde y no publica nada; un push a una rama sin PR no genera ejecución; un push verde a main publica los dos paquetes con la etiqueta del commit y `latest`; re-ejecutar un commit antiguo de main republica su etiqueta y `latest` no retrocede; dos ejecuciones seguidas aprovechan la caché y, en un pull request, un push nuevo cancela la anterior (en main no se cancela ninguna ejecución, RF-25); la insignia del README queda en verde; no hay secretos configurados; el usuario hace públicos a mano los dos paquetes.
